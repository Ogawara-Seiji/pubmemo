あなたは、初学者向けの技術勉強会を設計する講師兼プレゼンテーションデザイナーです。
以下の仕様に基づき、日本語のPowerPointスライドを作成してください。
対象読者、学習目標、スライド構成、技術的な前提、デザインルールを一つの仕様として扱い、全体を通して一貫した資料にしてください。

# 1. 作成する資料

タイトル：AIの変更、何が変わった？
サブタイトル：変更を把握するためのGit

- 用途：社内のGit勉強会。投影しながら講師が説明する資料。
- 対象：新卒入社から半年程度で、Gitを多少使ったことがあるエンジニア。
- 参加者にはベテランも含まれるが、説明の基準は初学者に置く。
- Gitの内部構造や、高度なコマンドの知識は前提にしない。
- 本編は60分。説明、デモ、参加者が考える時間を含める。
- 本編終了後、希望者向けの質疑応答を最大15分追加できる。
- 全22枚。本編18枚、付録4枚。表紙を枚数に含める。
- スライド比率は16:9。
- 言語は日本語。コード、コマンド、ファイル名だけ必要に応じて英語にする。
- 編集可能なPowerPointとして作成する。文章、表、コード、説明用の図は編集可能な要素にする。
- 日時、会社名、発表者名、会社ロゴは指定されていないため、架空の情報や仮置きの情報を追加しない。
- PowerPointファイルの作成ができない環境では、22枚それぞれの「タイトル・表示本文・図解指示・発表者ノート」を番号順に作成する。

# 2. 勉強会の中心に置く課題

参加者の困りごとは「AIが大きく変更したコードを、自分が把握できない」である。

この課題を入口に、Gitを使う理由とメリットを理解できる構成にする。
AIの話は、Gitを使う具体的な場面として扱う。

中心メッセージ：
「AIに依頼する → 変更を確認する → 採用して記録する、を小さく繰り返す」

Gitを使う価値を、次の行動と結びつける。
- 比較する基準を残す。
- 何が変わったかを確認する。
- 別の案を試す。
- 採用した変更と理由を残す。
- 問題が起きたときに履歴をたどり、対応する。
- 採用した変更をチームと共有する。

AIの性能に関する宣伝や、AIが必ず余計な変更をするという一般化は避ける。
教材のAI変更例は、学習のために用意した架空の変更であると発表者ノートに記す。

# 3. 参加後にできるようになってほしいこと

1. なぜ変更履歴を残すのか、Gitのメリットとともに説明できる。
2. AIの作業前後で、比較の基準と変更内容を確認できる。
3. 変更を採用する理由と、確認したことを説明できる。
4. AIへの依頼、確認、コミットを小さなまとまりで繰り返す使い方を理解する。

振り返りでは、次の問いに答えられる状態を目指す。
- どの状態を基準に変更したか？
- 依頼に対して、実際には何が変わったか？
- 何を確認し、なぜその変更を採用したか？

# 4. 説明の方針と扱う範囲

- 「困る場面 → 必要な考え方 → Gitの機能 → 操作後の確認」の順で説明する。
- コマンドは、その操作の目的が説明された後に補助として示す。
- 用語は初登場時に短く説明し、その後も同じ呼び方を使う。
- CLI、VS CodeなどのGUI、AIエージェントのどれを使っても通じる考え方を中心にする。
- 具体的なツールの画面操作に依存した説明は避ける。
- 参加者全員の環境構築は前提にせず、講師のデモと差分を見て考える形式にする。
- AIへのアクセスがなくても、事前に用意した差分で実演できる構成にする。
- ブランチや共有は、今回の使い方に必要な範囲で説明する。
- rebase、cherry-pick、Git Flow、Gitオブジェクトの内部構造、複雑なコンフリクト解消、Gitの導入や認証設定は本編の説明対象に追加しない。
- ベテラン向けの深掘りは、発表者ノートの任意の問いとして添える。
- 「Gitなら何でも戻せる」「コミットすれば正しい」「AIに任せれば安全」といった表現を使わない。
- 差分で変更内容を把握することと、動作確認やテストで振る舞いを確かめることを結びつける。

# 5. デザインシステム：オレンジを軸に統一する

## 5-1. 全体の印象

明るく、落ち着きがあり、読みやすい技術勉強会の資料にする。
白を主背景とし、オレンジを見出し周辺、重要語、図の注目箇所に使う。
広い余白を取り、一枚の中心となる図または比較を大きく配置する。

全ページが同じ資料に見えることを優先する。
同じ役割の要素には、必ず同じ色、フォント、文字サイズ、余白、線の太さを使う。

## 5-2. 色の指定

以下の色をテーマ色・標準色として統一する。

| 用途 | 色 |
| --- | --- |
| メインの濃いオレンジ | #C2410C |
| 補助の明るいオレンジ | #F97316 |
| 薄いオレンジの背景 | #FFF7ED |
| 通常の背景 | #FFFFFF |
| 本文・タイトル | #1F2937 |
| 補助説明 | #4B5563 |
| 罫線・区切り | #E5E7EB |
| コードの追加行の文字 | #166534 |
| コードの追加行の背景 | #F0FDF4 |
| コードの削除行の文字 | #B91C1C |
| コードの削除行の背景 | #FEF2F2 |

色の使い方：
- 濃いオレンジは、白背景上の強調文字や図の注目箇所に使う。
- 明るいオレンジは、細い線や装飾などに限定する。
- 明るいオレンジの背景に白い小さな文字を置かない。
- 緑と赤は差分の「追加」「削除」を示すときだけ使う。
- 差分には色とともに「+」「-」や「追加」「削除」の文字を付ける。
- 緑を正解、赤を不正解の意味に使わない。追加されたコードにも問題が含まれうる。
- 強調箇所は一枚あたり最大2か所を目安にする。
- ページごとにアクセントカラーを変えない。

## 5-3. フォントと文字サイズ

日本語の基本フォント：游ゴシック（Yu Gothic）
英数字も、通常の文章では同じフォントを使う。
コード・コマンドの英数字：Consolas
コード内の日本語は、本文と同じ日本語フォントを使う。

游ゴシックが使えない場合は、利用可能な日本語ゴシック体を一種類だけ選び、全体を一括で統一する。
ページごとに別のフォントへ置き換えない。

文字サイズ：
- 表紙のタイトル：44pt、太字。
- 表紙のサブタイトル：28pt。
- 通常スライドのタイトル：32pt、太字。
- 通常の本文：24pt。
- 図のラベル・表・コード：20pt。
- フッター・出典の短い表記：14pt。

文字サイズを細かく増やさない。
文字が収まらない場合は、説明を短くするか、詳細を発表者ノートへ移す。
本文の文字を小さくして詰め込まない。

## 5-4. レイアウト

- 左右の余白は約0.6インチ以上確保する。
- タイトルの位置と本文の開始位置は、通常スライドで統一する。
- タイトルは原則一行。必要な場合でも二行以内。
- 本文、図、表の左端をそろえる。
- 通常の説明スライドは、本文を目安120〜160字以内にまとめる。コード、表、注記、タイトルを除く。
- 箇条書きは原則3項目以内、最大4項目。階層は原則一段にする。
- 一枚に置く中心メッセージは一つにする。
- 右下に「01 / 22」形式でページ番号を置く。
- 通常ページの左上に短いオレンジのアクセント線を置き、同じ位置・同じ太さを使う。
- 影、立体表現、グラデーション、過剰な角丸は使わない。
- カードや枠を並べる構成を繰り返さず、文章・比較・図解の関係が自然に見える配置にする。
- アニメーションがなくても説明が成立するようにする。

## 5-5. 図・表・コード

- 図は、今回指定する履歴、状態、比較、共有を説明するための編集可能な図として作る。
- 矩形、丸、矢印、線、文字ラベルのスタイルを統一する。
- 矢印は関係や操作が明確な場合に使い、ラベルを付ける。
- 横に並べる主要な要素は最大4個を目安にする。
- 図中の記号や色の意味を途中で変えない。
- 表は、薄いオレンジの見出し行と白い本文行を基本にする。
- コードは画像化せず、編集できるテキストとして配置する。
- 本編のコードは一つのブロックあたり原則8行以内にする。
- 差分の前後関係を示す行は残すが、Gitのヘッダーなど説明に不要な部分は省略してよい。その場合は「差分抜粋」と明示する。
- 写真、人物、ロボット、握手、抽象的なAIイラストなどの装飾画像は追加しない。
- 架空のIDE画面、読めないターミナル画像、架空のGitHub画面は作らない。
- ロゴは不要。

# 6. 日本語と表記のルール

- タイトルは簡潔な名詞句、またはそのページで答える具体的な問いにする。
- 大げさなコピーや「革命」「最強」「究極」などの表現は使わない。
- タイトル末尾の句点「。」は付けない。
- 本文の説明文は「です・ます」調に統一し、短いラベルは名詞句にする。
- 同じ概念を「保存」「確定」「登録」などと言い換え続けない。必要に応じて操作を明確に呼び分ける。
- 「保存」はエディタでファイルを保存すること、「コミット」はGitの履歴に記録することとして区別する。
- Git、GitHub、AI、コミット、ブランチ、差分、ステージ、ローカル、リモートの表記を統一する。
- main、ai/name-message、src/validation.jsなどのコード・名前は全ページで同じ表記にする。
- AIは初登場時に「コードの変更を支援するAI」と説明する。特定のコード生成サービスだけを想定しない。
- ここでいうMicrosoft Copilotは資料の作成先であり、勉強会の題材をMicrosoft製品の操作講習に変更しない。
- 「ベテランなら当然」「初心者はやりがち」といった参加者を評価する言い方はしない。

# 8. 全編で使う教材

教材は、小さなJavaScriptの入力チェック処理とする。
JavaScriptの高度な文法知識がなくても読めるように説明する。

教材の入力は文字列に限定する。
既存の仕様：
- 空文字のユーザー名はエラー。
- 1文字以上のユーザー名は受け付ける。
- エラーがない場合はnullを返す。
- 今回の依頼は、エラーメッセージの改善だけ。受け付ける文字数は変えない。

AIへの最初の依頼例：
「名前が未入力のときのエラーメッセージを、わかりやすくしてください」

教材のファイル：
- src/validation.js：入力チェック処理。
- tests/validation.test.js：入力チェックのテスト。
- src/format.js：今回の依頼とは関係のない整形処理。

AIが行った変更として用意するもの：
1. エラーメッセージを変更する。
2. そのメッセージを確認するテストの期待値を変更する。
3. 空文字だけを弾く処理を、3文字未満を弾く処理へ変更する。
4. src/format.jsの無関係な書式を変更する。

重要な教材の狙い：
- 実装と対応するテストなど、一緒に必要になる変更がある。
- 同じファイル、同じ行の中にも、意図した変更と意図していない変更が混ざる。
- ファイル単位で選べば必ず解決する、とは説明しない。
- 意図しない条件変更は、実装を修正し、テストを確認してから記録する。
- git add -pで同じ行の意味まで自動的に分けられるような説明はしない。

変更前のコード：
    export function validateName(name) {
      if (name === "") return "入力エラー";
      return null;
    }

AIの変更例：
    export function validateName(name) {
      if (name.length < 3) return "名前を入力してください";
      return null;
    }

今回採用したいコード：
    export function validateName(name) {
      if (name === "") return "名前を入力してください";
      return null;
    }

確認する入力と期待する結果：
- "" → "名前を入力してください"
- "AI" → null
- "Alice" → null

AIの変更例では"AI"もエラーになる。
この挙動が既存仕様から変わっていることに、差分と確認ケースから気づく構成にする。

# 9. スライドごとの詳細指示

以下の順序と役割を守る。
各ページの「伝えること」は中心メッセージであり、説明文をそのまま全部スライドに詰め込まない。
詳細な説明と補足は発表者ノートに入れる。

## スライド1：表紙

タイトル：AIの変更、何が変わった？
サブタイトル：変更を把握するためのGit

- タイトルとサブタイトルを大きく配置する。
- 背景は白または薄いオレンジ。
- 濃いオレンジの細い線でアクセントを付ける。
- 内容一覧、説明文、学習目標を同じページに追加しない。
- ノートでは、AIを使う日常の困りごとからGitを考える会だと説明する。

## スライド2：AIの変更を把握できない

伝えること：変更された量と、自分が説明できる範囲の間にギャップがある。

表示する状況：
- AIが複数のファイルを変更した。
- 動いているように見える。
- でも、何を採用してよいか判断できない。

- 中央に、参加者への問い「この変更、そのまま採用できますか？」を置く。
- src/validation.js、tests/validation.test.js、src/format.jsを短く示してよい。
- 架空の変更行数や、生産性に関する数字は追加しない。
- ノートに、30秒ほど考えてもらう進行を入れる。ここでは正解を先に出さない。

## スライド3：今日のゴール

伝えること：Gitを使って、変更を把握し、採用する理由を説明できるようになる。

表示する問い：
- どの状態を基準にした？
- 実際には何が変わった？
- 何を確認し、なぜ採用した？

- 三つの問いを読みやすく配置する。
- コマンド一覧や高度な用語は置かない。
- ノートに、本日の中心メッセージを添える。

## スライド4：変更履歴を残す理由

伝えること：現在のファイルだけでは、変更の経緯をたどりにくい。

- 「変更前」「変更後」「問題が起きた後」の関係を図で示す。
- 過去との比較、記録した状態の参照、変更理由の確認を説明する。
- 変更理由は、人がコミットメッセージなどに残す情報であると補足する。
- Gitが変更の意図を自動で理解・記録すると誤解させない。
- ノートでは、自分一人の作業でも履歴が役立つ例を一つ話す。

## スライド5：Gitでできること

伝えること：Gitは、手元で履歴を作り、試行を分け、履歴を共有する仕組みを提供する。

表示する要素：
- 手元で変更履歴を記録する。
- 共通の履歴から別案を試す。
- 履歴を共有先へ届ける。

- シンプルな関係図で表す。
- Gitの全操作に通信が必要だと思わせない。
- 他のバージョン管理システムにも共通する価値があることはノートで短く補足してよい。
- 分散型という用語の暗記や、他ツールとの詳細比較に時間を使わない。

## スライド6：作業・ステージ・履歴

伝えること：編集した内容と、次のコミットに記録する内容を分けて考える。

必ず示す三つの状態：
1. 作業ツリー：いま編集しているファイル。
2. ステージ：次のコミットに記録する内容。
3. 履歴：コミットとして記録した状態。

- 三つを横に並べた図にする。
- 作業ツリーからステージへ向かう矢印にgit addと書く。
- ステージから履歴へ向かう矢印にgit commitと書く。
- 「ファイルの保存だけではコミットされない」を短く添える。
- このモデルをスライド9でも同じ色、同じ配置で再利用する。
- ノートでは、git add後に再編集した内容は、再度ステージしない限り次のコミットへ自動で入らないことを補足する。
- コミットは選んだファイルだけの差分を保存するもの、と断定しない。技術的には、その時点で記録対象となるプロジェクトのスナップショットを記録し、親のコミットとの比較で差分を確認できる。

## スライド7：AIに頼む前の確認

伝えること：変更前の状態がわかると、AIの変更と元の作業を区別しやすくなる。

表示する行動：
- いまの変更を確認する。
- 既存の作業を整理し、必要な区切りを記録する。
- 今回の依頼範囲を決める。

補助として示すコマンド：
    git status
    git diff

- すべての変更を無条件に一括コミットする説明にしない。
- ノートに、講師の教材は既存の基準コミットがあり、作業ツリーがクリーンな状態から始めると記載する。
- 今回の実演中、AIはまだステージングやコミットをしていない前提にする。
- AIが自動でコミットする運用では、作業後に履歴と比較対象も確認する必要があることはノートの補足に留める。

## スライド8：一つの依頼に混ざった変更

伝えること：依頼内容と、実際の変更範囲を対応づけて見る。

- 最初の依頼文を示す。
- 変更を「メッセージ」「テストの期待値」「入力条件」「無関係な整形」の四つに整理する。
- この時点では採否の答えを全部書かない。
- 実装とテストは別ファイル、メッセージと入力条件は同じ行に混ざっているとわかるようにする。
- ノートでは、この教材が説明用に準備した変更例であることを明示する。

## スライド9：差分の比較対象

伝えること：差分を見るときは、何と何を比べているかを確認する。

- スライド6の三つの状態を、同じ配置で示す。
- git diff：ステージと作業ツリーの比較。
- git diff --cached：直近のコミットとステージの比較。
- それぞれの比較範囲を、対応する二つの状態を結ぶ線で示す。
- 「git diffが空＝未コミットの変更が一切ない」と説明しない。
- 未追跡ファイルは通常のgit diffに表示されないため、git statusも確認することをノートに入れる。
- git diff HEADは、直近のコミットと現在の作業ツリーを比較する補足としてノートだけに置いてよい。

## スライド10：差分から仕様変更を見つける

伝えること：表示文言の変更と、入力を受け付ける条件の変更を分けて読む。

差分抜粋として、必ず以下の内容を使う。

     export function validateName(name) {
    -  if (name === "") return "入力エラー";
    +  if (name.length < 3) return "名前を入力してください";
       return null;
     }

- コードを大きく配置する。
- 「メッセージが変わった」「判定条件も変わった」の二つの注釈を付ける。
- 追加行は緑、削除行は赤で示す。記号の+と-も残す。
- ノートで、"AI"という2文字の入力を例に挙げる。
- 行数が少なくても意味の大きな変更がありうることを説明する。
- 架空のGit出力全体やハッシュ値を作り込まない。

## スライド11：どの変更を採用する？

伝えること：依頼と既存仕様を基準に、変更を判断する。

- 四つの変更を表にする。
- 表示する列は「変更内容」「確認したいこと」にする。
- 採否の答えは発表者ノートに置き、最初からスライド本文で答えを見せない。
- 考える時間を60秒程度取る。
- 正解の早押しにせず、判断の理由を聞く進行にする。

ノートに置く判断例：
- メッセージ：意図に合えば採用する。
- 対応するテストの期待値：実装変更と一緒に更新する必要がある。
- 入力条件：依頼にも既存仕様にもないため、今回の修正で元の条件へ戻す。
- 無関係な整形：今回必要か確認し、必要なら別の目的の変更として扱う。
- 「ファイルで分ければよい」では、同じ行に混ざった条件変更を除けないことに触れる。
- ベテランには「変更同士に依存がある場合、どこまでを一緒に記録するか」を任意で聞く。

## スライド12：差分の確認と動作の確認

伝えること：変更箇所の把握と、期待する振る舞いの確認を組み合わせる。

表示する確認ケース：
- 空文字 → 新しいメッセージになる。
- "AI" → 引き続き受け付ける。
- "Alice" → 引き続き受け付ける。

- 「入力」「期待する結果」「AI変更例の結果」の比較表にする。
- "AI"の行で、既存仕様と異なる振る舞いになったことを明示する。
- 差分の追加・削除に使った赤緑を、表の正誤判定には使わない。
- オレンジの強調と「仕様と不一致」の文字で注目箇所を示す。
- ノートでは、メッセージだけを確認するテストは通っても、文字数条件の変化を検出できない場合があると、この教材に限定して説明する。
- 期待する結果が何に基づくかを明示する。

## スライド13：採用するまとまりを記録する

伝えること：確認した実装と、対応するテストを説明できるまとまりで記録する。

- 入力条件を元に戻し、メッセージだけを改善したコードを採用する。
- 対応するテストを確認する。
- ステージした差分を確認し、コミットする。
- コミットメッセージ例は「名前未入力時の案内文を改善」とする。
- 実装と対応するテストの二つが一つの目的を持つことを図で示す。
- 無関係な整形を、同じ目的の変更としてまとめない。
- 同じ行に混ざった変更は、実装を修正したうえで記録する。

ノートに入れる操作例：
    git add src/validation.js tests/validation.test.js
    git diff --cached
    git commit -m "名前未入力時の案内文を改善"

- ノートでは、採用しないと判断したsrc/format.jsの差分を確認したうえで、そのファイルに限って編集を破棄する手順を入れる。教材では未ステージの編集だけなのでgit restore -- src/format.jsを使う。最終的にgit statusで意図しない編集が残っていないことを確認する。
- ノートでは、確認後にソースを再編集した場合は、再ステージと差分確認が必要になることを補足する。
- AIが生成したコミットメッセージも、実際の差分と一致するか確認する。

## スライド14：AIへの依頼を小さく区切る

伝えること：依頼、確認、記録を一回ごとに完了できる範囲へ区切る。

- 改善した依頼例を示す。
- 例文：
  「空文字のときのメッセージを『名前を入力してください』に変更してください。受け付ける文字数の条件は維持してください。対応するテストを更新し、既存の入力が引き続き受け付けられることを確認してください」
- 長い依頼文は表示用に短く整理し、完全な例文はノートに入れてよい。
- 依頼の範囲、維持したい仕様、確認方法がわかるようにする。
- 明確な指示を出しても、作業後の差分と動作の確認を行う。
- 複数の仕様変更がある場合は、確認できる単位で依頼を分ける例をノートに入れる。
- 「小ささ」は行数だけでなく、一つの目的を説明できるかでも考える。

## スライド15：別案を試すブランチ

伝えること：共通の履歴を出発点に、別の作業の履歴を進められる。

- 教材の基準コミットをC0と表す。
- mainはC0を指す。
- ai/name-messageでC1、C2とコミットが進む図にする。
- ブランチ名が履歴の先端のコミットを指していることがわかるようにする。
- C0、C1、C2は図を読むためのラベルであり、実際のコミットIDではない。
- 補助としてgit switch -c ai/name-messageを示してよい。
- ノートで、AIに試してもらう前にブランチを用意する使い方を説明する。
- ブランチを作るだけで未コミットの編集が別々に保存されるような説明にしない。
- ブランチ切り替えで未コミットの変更が自動保存されるような図にしない。

## スライド16：何を取り消したい？

伝えること：記録前の編集を破棄する場合と、記録済みの変更を打ち消す場合を区別する。

表示する二つの場面：
1. 対象ファイルの未コミット・未ステージの編集を捨てたい。
2. コミットした変更を、打ち消した記録を追加して取り消したい。

- 二つの場面を比較する。
- 1にはgit restore -- src/validation.jsを対応づける。
- 2にはgit revert HEADを対応づける。
- restoreの例では、対象ファイルにステージ済みの変更がない前提を明示する。
- 「restoreでは対象の編集が失われる」を短く、通常の補足文として表示する。
- revertは直前の単独の通常コミットを対象にした教材例とする。
- revert後も、元のコミットが履歴に残ることを図で示す。
- ノートでは、通常のrestoreはステージの内容から作業ツリーへ復元することを説明する。
- revertの実演は作業ツリーがクリーンで、打ち消す内容が明確な教材で行う。
- 履歴を書き換える高度な操作へ話を広げない。

## スライド17：記録した変更を共有する

伝えること：手元で履歴に残すことと、共有先へ履歴を送ることは別の操作である。

- ローカルのリポジトリと、リモートのリポジトリを区別する。
- commitはローカルの履歴を作る操作、pushは共有先を更新する操作として示す。
- Gitはバージョン管理の仕組み、GitHubはリポジトリのホスティングやレビューを支援するサービスの一例、と短く説明する。
- Gitの利用にGitHubへの接続が常に必要だと思わせない。
- レビューでは「何を変更したか」「何を確認したか」を共有する例をノートに入れる。
- pullやmergeの操作方法、PR画面の詳細解説は追加しない。

## スライド18：次のAI作業で確かめること

表示する振り返りの問い：
- どの状態を基準にした？
- 実際には何が変わった？
- 何を確認し、なぜ採用した？

# 10. 発表者ノートの仕様

各スライドに、日本語で発表者ノートを付ける。
通常の説明ページは200〜400字程度を目安にし、コードや参考URLは別枠で追記してよい。
表紙、質疑、参考資料のページは必要な長さに調整してよい。
デモページは、必要な手順を省かずに書く。

ノートに含める内容：
- そのページで伝える中心メッセージ。
- 初学者に向けた自然な説明。
- デモで見せる操作と、そのときの比較対象。
- 参加者への問いと、講師が押さえる判断例。
- 誤解しやすい点の補足。
- 目安時間。
- 技術的な説明に対応する公式資料のURL。

問いを置くページは、問いを見せるタイミング、考える時間、解説するタイミングまで書く。
高度な補足は、講師が必要なときに使える任意の説明として区別する。
ノートの文章をそのままスライド本文に移さない。

# 11. 技術的な正確性

特に次の点を確認してから完成させる。

- GitとGitHubを同一視しない。
- 保存、ステージ、コミット、pushを区別する。
- 通常のgit commitはステージの内容をもとに新しいコミットを作る。
- git add後の再編集が、再ステージなしでコミットされると説明しない。
- git diffとgit diff --cachedの比較対象を取り違えない。
- 未追跡ファイルまで通常のgit diffで確認できると説明しない。
- ブランチは、履歴の先端を指す参照として扱う。
- 未コミットの変更が、ブランチを作っただけで別の履歴として記録されると説明しない。
- コミットメッセージに人が理由を書くことと、Gitが自動的に意図を理解することを混同しない。
- Gitは記録した内容や履歴を扱うもので、コードの正しさやテストの成功を保証しない。
- Gitの履歴だけで、依存パッケージ、外部サービス、データベースなどの実行環境もすべて復元できると説明しない。
- restoreとrevertは目的、対象、履歴への影響が違う。
- 教材の既存仕様、差分、確認ケース、採用コード、コミット内容をすべて一致させる。
- コードやコマンドの引用符には半角の"を使い、装飾的な引用符に変えない。
- 説明図の矢印、コミットの順序、ブランチ名の位置を、説明と一致させる。

# 13. 作成・仕上げの手順

1. 学習目標とスライド1〜22の役割を読み取り、構成を維持する。
2. 配色、フォント、文字サイズ、標準レイアウトを、テーマまたはマスター相当の共通ルールとして設定する。

6. 全ページを見渡し、フォント、色、余白、表、コードのスタイルをそろえる。
7. 文字のはみ出し、重なり、不自然な改行、小さすぎる文字、切れたコードがあれば修正する。
8. 本編60分、付録4枚、全22枚であることを確認して完成させる。

機能上、指定の一部を反映できない場合は、その箇所と代替の反映内容だけを資料外のメッセージで簡潔に伝える。
